# 与 Workloop 的逐项对比

状态：2026-11-21，供 P8 及后续阶段取舍。P4.8 说要“把 Workloop 的开发流程做成产品自身的能力”，本文逐项核对做到了哪些。

参考的是 `paseo-matt-workloop` 仓库 `rex-local` 分支 `222b4ff` 的全部技能，原样拷贝在 [vendor/workloop-skills](../vendor/workloop-skills/SOURCE.md)。对照的是本仓库的 Main 基础层 `.pi/prompts/cowork-main.md`、`requirement-delivery` 技能、`project_development` 与 `project_ledger` 工具、Executor 与 Reviewer 的提示词（`.pi/runtime/subagent-agent.ts`、`src/domain/development-ticket.ts`）和数据表。

结论：**合入以前的骨架基本照搬了**（三条路线、票、冻结、改动范围、合入时先跑检查再跑验收命令、终审、修复票）；**骨架两头和审查的规矩大多没有**：开工前怎么弄清需求和已有约定，审查能拦什么、返修几轮为止，交付后怎么复盘、怎么留经验。

## 一、已经一致的

| 环节       | Workloop                                                       | 我们                                                        |
| ---------- | -------------------------------------------------------------- | ----------------------------------------------------------- |
| 路线       | Quick / Direct / Full，按不确定性和影响选，不按行数            | `quick` / `direct` / `full`，技能里写了怎么选               |
| 票的字段   | 要做什么、保留不变、本次不做、依赖、改动范围、带编号的验收标准 | 同样字段                                                    |
| 验收标准   | 每条写检查命令或“为什么只能人工”；不用无边界的词               | 同样                                                        |
| 确认与冻结 | 用户确认后冻结，改动要记录用户的决定和理由                     | 确认卡片；`revise_ticket` 带理由                            |
| 改动范围   | 冻结候选时超出范围的改动被拒                                   | 同样                                                        |
| 合入       | 先跑项目检查，再跑本票验收命令，失败回滚                       | 同样                                                        |
| 返修       | 合入前回原 Executor 的会话；合入后的缺陷开新的修复票           | 同样                                                        |
| 终审       | `full` 路线全部票合入后，独立终审看整体                        | 同样                                                        |
| 下一步     | 脚本的 `status` 给出下一步                                     | 每次结果带 `next`                                           |
| 项目说明   | 每次会话读项目的 AGENTS.md                                     | 项目的 AGENTS.md 自动放进 Main 的提示词（已在真实会话核实） |

## 二、有但做法不同的

| 环节       | Workloop                                                                                                                                                                                                                                               | 我们                                                                                                           | 差在哪                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 需求台账   | 一条需求是一块长期功能，挂多次开发；正文是一直更新的现状；别名；按原话查归属，找不准列全部目录；`context` 一次取回现状和指针；交付后同步                                                                                                               | 一条需求只能有一条开发记录，等于“一次开发”；决定挂在需求下；只有标题和正文的字面查找                           | 见 [上下文检索增强设计](context-retrieval-design.md)                   |
| 执行者说明 | 说明书写明：先读踩坑记录；按 tdd 在约定的测试位置写；加的测试必须放在合入检查会跑到的地方；只停自己启动的进程；不加没要求的文档；与架构决定冲突就停下报 `question`；文档和代码不一致以代码为准；汇报格式固定（状态、提交、摘要、逐条验收、检查、问题） | 票的内容 + “提交并跑检查命令”；“超出说明就问 Main”；交回三部分（结果、证据、试过没走通的）                     | 少了测试放哪、架构决定、踩坑记录、进程和文档几条；汇报不逐条对验收标准 |
| 审查       | 拦截性发现必须注明依据：某条验收标准，或四类底线之一（回归、丢数据、安全、违反架构决定）；其余一律写成“范围外建议”，不拦截；执行者的汇报只当声明；审查者自己重跑每条验收命令                                                                           | 先逐条查验收标准，再找“没覆盖的”：保留行为坏了、超出范围、缺测试；每条发现写位置、证据、是否拦截，没有依据一栏 | 审查能拦什么没有边界，审查者可以每轮提新要求                           |
| 复审       | 只做三件事：确认上一轮每条拦截性发现修好没有（编号不变）、重跑验收命令、查这一轮改动里的底线问题；不提新发现                                                                                                                                           | 和首次审查一样，从头审                                                                                         | 复审会越审越多                                                         |
| 返修消息   | 先复现再修；修原因不修表象；交回前自查改动；汇报逐条写哪个测试先红后绿                                                                                                                                                                                 | 交回原 Executor，没有固定做法                                                                                  | —                                                                      |
| 终审       | Main 先写“验收对照表”（每行一条方案要求和证据），终审逐行核实；重跑全部检查；复核每条放行；真跑一遍改动；后几轮同样收窄                                                                                                                                | 看整体是否满足需求、各部分是否接得上                                                                           | 没有对照表，终审没有逐条可核的东西                                     |
| 修复票     | Main 自己在集成版本上复现，贴出命令和输出；已知原因和猜测分开写                                                                                                                                                                                        | 开新的修复票，没有写法要求                                                                                     | —                                                                      |
| 完成汇报   | 列出全部放行记录、超出上限的轮次、范围外的拦截性发现，建议汇总成一个文件只报条数和路径                                                                                                                                                                 | 写改了什么、证据、遗留                                                                                         | 用户看不到放行了什么                                                   |

## 三、没有的

### 开工前

- **先查再澄清**：用户一提需求，先用原话查台账是哪条需求，再开始问。
- **读架构决定和用词表**：动手前读与要改区域相关的架构决定（`docs/adr/`）和 `GLOSSARY.md`；与已有决定冲突要明说，由用户决定。
- **先复述再设计**：提方案前先列出“要改的”和“从用户反馈里看出必须保留的”；用户说还有补充时先收齐。保留的行为写进票的“保留不变”。
- **追问**（grilling）：重要问题按依赖分轮问，每轮把能问的一次问完，每题附推荐答案；能查到的事实自己查，不问用户。
- **选定的边界要指出来**：票里哪些保留、哪些删除、哪些情况算数，凡是 Main 自己定的，提交确认时点明。

### 决定的记录

- **架构决定**（ADR）：难以回头、不看背景会奇怪、确有取舍三条都满足才写；讨论中定下的，随本次开发的第一个提交一起合入，执行者从包含它的版本开始。
- **推翻**：写新的、删旧文件、在 `docs/adr-history.md` 加一行，`docs/adr/` 里只剩生效的。决定依赖的前提可以写一行 `Premise:`，以后好检验。
- 执行者和审查者都把生效的架构决定当作用户早先的决定：执行者冲突就停下问；审查者把违反列为底线问题。

我们现在没有这套：用户项目里的决定记在台账的“决定”里，执行者和审查者看不到。

### 审查和返修的约束

- **返修上限**：每张票默认 2 轮，超过就停下问用户，用户同意才加轮，并记录理由；终审的修复轮次同样有上限。
- **放行记录**：Main 判定某条拦截性发现不用修时必须写理由，记入放行记录；完成时整份列给用户。
- **范围外建议汇总**：所有审查的范围外建议汇总成一个文件，完成时只报条数和路径。

### 交付以后

- **复盘**（retro）：每次完整开发结束看四类信号：外部依赖反复出错、业务含义反复误解、反复做错的动作、反复重复的探索。每条发现写“发生了什么和证据 → 什么能帮上 → 改在哪”，改动位置从“结构上杜绝”到“写进说明”依次考虑。只提建议，用户决定。
- **踩坑记录**：复盘里属于这个项目的坑，经用户同意写进项目的 `docs/pitfalls/`，一条一个触发点和一个出路，带一个今天还能跑的确认方法；执行者开工前读触发点相关的。
- **健康检查**（workloop-audit）：从运行记录里数审查、返修、交付，标出与规矩不符的地方，供复盘和跨多次开发的回顾。

### 文档整理

- **文档登记表**：项目的 AGENTS.md 里一张表登记每份文档的类型和领域；每次完整开发结束检查新加的文档有没有登记，过程文档（计划、进度、交接）不留在仓库里。

### 验证证据

- **固定候选的检查**：审查和终审跑命令前后对比工作区，检查期间工作区被改动就算失败；每次运行留回执，第一次失败的记录不被后来的成功覆盖。我们的审查者在自己的副本里跑，候选不会被改，但没有回执，失败记录靠会话。

### 通用技能

Workloop 带着、我们没有内置的：查疑难问题（diagnosing-bugs：先做出能稳定复现的检查再猜原因）、测试驱动（tdd）、追问（grilling）、领域建模（domain-modeling：用词表和架构决定）、写给助手的文档（writing-for-agents）、模块设计（codebase-design）、交接（handoff）。我们内置的只有 `requirement-delivery` 和电脑操作。

## 四、我们有而 Workloop 没有的

- 用户和 Main 看同一份进度：票和状态在看板、交付视图里。
- 票的确认在界面上点，不靠对话。
- 多个 Main 共用一个合入入口，合入前与目标分支最新版本组合再检查。
- 子助手可以向 Main 提问、彼此发消息；Workloop 的执行者只能停下报 `question`。
- 记忆（跨会话的协作习惯）。

## 五、谁来决定

Workloop 假定身边一直有一个懂技术的用户可以问。我们不是：对内 Main 的用户可能不在，对外 Main 不直接面对人，需求来自不懂技术的客户，只能经 Router 转述，回复可能隔很久。所以 Workloop 里交给用户决定的地方，在我们这里分三类（2026-11-21 与用户确认）。

### Main 自己定，记下理由，事后可查

| Workloop 交给用户的            | 我们                                                                                                       |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 返修超过上限要用户同意         | 上限是给 Main 的刹车：到了上限必须换办法（重新拆票、换思路、先交付做好的部分并说明没做的），不原样再改一轮 |
| 终审修复超过上限               | 同上                                                                                                       |
| 放行审查拦下的问题             | Main 定，写理由，进放行记录                                                                                |
| 审查的范围外建议               | Main 挑要做的，其余汇总留档                                                                                |
| 扩大改动范围、direct 改成 full | 只要还在需求范围内，Main 定并记下理由                                                                      |
| 票里哪些保留、哪些删除         | Main 定，写进票                                                                                            |
| 写踩坑记录、采纳复盘建议       | Main 写，记录可查，负责人随时可以删                                                                        |

### 只有提需求的人能定

只有会改变对方拿到什么的事：需求到底什么意思、产品该怎样表现、要不要推翻对方以前定下的规矩。

- 对外：经 Router 用客户能懂的话问。问出去后保存会话分支和工作进度、挂起需求，常驻 Main 继续领新需求；回复到达后由接续 Main 从该分支接着做，再要等就再保存分支并退出。客户没有回复时定时再催，最多 3 次，之后通知负责人。见 [开发阶段规划](development-phases.md#p5对外接单回访与接续)。
- 对内：用提问工具问用户，继续做不依赖答案的部分。

让对方确认的是一段大白话：做完以后哪些地方会变、哪些保持不变。票是 Main 的施工计划；对内是否保留票的确认卡片另定。

### 程序挡住，谁也不问

推送、越过需求归属合入、删除范围外的文件等，由程序拒绝。

### 汇报给谁

放行记录、建议汇总、没做完的部分：对内报给用户；对外报给项目负责人，放在看板上，客户只收到结果。

## 六、下一步做什么

上面“没有的”不必全做。按对结果的影响，建议的先后是：

1. **审查边界、复审收窄、返修上限、放行记录**：直接决定开销和会不会越改越多。`team` 测评那次 direct 用了 780 万 tokens、审了两轮，正是这一块。
2. **开工前**：先查台账、读架构决定、先复述保留的行为。这是 P8 要解决的“守住以前的规矩”的入口。
3. **需求台账改成长期功能**，以及**架构决定**放在用户项目里：两者一起决定规矩记在哪。
4. **复盘和踩坑记录**。
5. **文档登记、验证回执、通用技能**。

## 七、第 4 项：复盘和踩坑记录（2026-11-22 定）

### 用户的两条决定

- **复盘和写坑点都自动做。** 不等用户同意；写了哪些坑点在交付汇报里列出，负责人随时可以删。与第五节"写踩坑记录：Main 写，记录可查"一致。
- **只写能复用的经验，不写细节。** change-bot 的记录有这个问题：坑点里写死了设备型号（DH-P5A）、一整行探针命令、要先装好的镜像；复盘里写提交号、失败用例数、哪一轮审查发现的。下一个人碰到的是"新检出不带被 Git 忽略的环境文件"这一类情形，不是那一次的经过。

### 怎么做

复盘是一个动作，产出只有坑点；坑点是给仓库用的，跟着仓库走，谁在这个仓库里干活都能读到。复盘本身不另存记录，也不产出别的建议。

**复盘（动作）**

- 一个需求做一次，在需求交付、最后合入之前：不论拆了几张票、审了几轮、返修几轮，都只在最后看一遍整个需求。结果是新增、合并或删除了哪些坑点，或者"没有要记的"。没做，程序不放行需求的最后合入。
- 程序先从这个需求的全部记录里数出信号交给 Main：返修轮数、到了上限的票、被放行的拦截发现、合入检查失败、协作者失败或重派、提问超时。信号全为零时，程序自动记"没有要记的"，不占 Main 的回合。
- 从信号里找的是这个仓库的坑：它的代码、配置、环境，或它用到的工具、外部系统在这里的表现，让顺手的做法出错的地方。看 Workloop 的四类：外部依赖反复出错、业务含义反复误解、反复做错的动作、反复重复的探索。只出现一次、当场就解决的普通返修不算。
- 不是坑的不记：怎么干活的通用建议（"先看原始日志"）、智能体越权（按名字杀进程），都与仓库无关。

**坑点**

- Main 在这个需求的检出里写进 `docs/pitfalls/`，与需求一起合入，用户在合入的改动里能看到。
- 每条一个触发情形、一个出路，五项：触发、会怎样、怎么确认、怎么避开、来源。同一触发、同一出路的，只在原条目的来源里加一行。
- "不写细节"由程序检查，不靠提示词：每项一到两句；不许出现提交号、绝对路径、票号、轮次和用例数；"来源"只写需求标题和日期。"怎么确认"是一句能做的检查，不强求一整行命令。不合格的条目，程序拒收并说明哪一项超了。
- 每次写坑点都顺带整理整份坑点文档，不让它越积越长：
  - 合并：触发情形相同或相近、出路相同的合成一条，来源并到一起；
  - 删除：坑已经不在了的（代码改掉了、已有测试或程序检查挡住了、"怎么确认"已经确认不出来），直接删掉；
  - 暂不限制条数，索引一条一行。
  - 整理的结果（新增、合并、删除各几条）和新写的坑点一起列进交付汇报。
- 读：用户项目里有 `docs/pitfalls/README.md` 时，程序把索引放进 Executor、Reviewer 的任务说明，Main 打开开发记录时也拿到。条目和代码对不上时以代码为准，下次复盘删掉这条。

### 不做的

- 健康检查（跨多次开发统计）先不做，等有真实使用数据。
- 不把复盘过程或日志摘录复制进用户仓库，坑点的来源只写需求标题和日期。
