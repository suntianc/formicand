# 测试

简体中文 | [English](en/testing.md)

按改动范围选测试：改什么测什么，失败只重跑失败的部分。全量测试只留给发版和影响面大的改动。各命令的作用见 [开发](development.md#检查命令)。

## 测试分层

| 层         | 位置                               | 证明什么                                     | 不能证明什么             |
| ---------- | ---------------------------------- | -------------------------------------------- | ------------------------ |
| Node 测试  | `test/`                            | 函数、服务、协议、真实 Pi 进程的生命周期     | 页面交互、真实模型的能力 |
| 浏览器测试 | `e2e/`                             | 页面和后端联动的用户流程                     | 干净机器上的安装         |
| 桌面测试   | `npm run test:desktop`             | 打包后的 App：设置、会话、退出重启、模拟升级 | 签名、公证、真实系统权限 |
| 原生测试   | `npm run test:release -- --native` | 真实窗口、输入和系统权限                     | 商业软件里的完整任务     |
| 真实模型   | 手动配置后运行                     | 真实服务的请求和代表性任务                   | 别的服务和别的模型       |
| 安装验收   | 最终 DMG 装到另一台 Mac            | 首次启动、连接、恢复、备份和升级             | —                        |

上一层通过不能替代下一层。本地假模型能证明协议和生命周期正确，不能证明模型能力。

## 日常跑测试

```sh
npm run test:unit -- --file test/artifact-store.test.js   # 指定文件，可重复 --file
npm run test:unit -- --match artifact                     # 路径包含 artifact 的文件
npm run test:unit -- --list --match artifact              # 只列出，不运行
npm run test:unit -- --skip-build --file test/x.test.js   # 已有当前源码的构建时跳过构建
node --test test/repository-checks.test.js                # 不依赖构建的纯脚本测试
```

- `--file` 是精确路径，`--match` 是区分大小写的路径子串，两者不能同时用。拼错或匹配为空会直接失败。
- `test/` 下的 `.test.js`、`.test.mjs`、`.test.ts` 都会被自动发现，`.ts` 跑的是编译结果。
- `--skip-build` 只在构建和当前源码一致时用，旧 `dist/` 的通过不算数。
- 测试数和跳过数以本次运行为准，不要引用以前的通过计数。退出码 0 不代表跳过的部分验证过。

浏览器测试：

```sh
npx playwright install chromium      # 第一次需要
npm run test:browser                 # 构建后跑全部
npx playwright test e2e/conversation-menu.spec.js --output=.tmp/playwright-menu
```

同时跑多个 Playwright 进程时，每个用不同的 `--output`，否则会清掉对方的产物。

## 写测试的规矩

- **隔离数据。** 用临时目录和假模型服务，不读个人配置，不碰真实任务，不调用真实模型。
- **临时目录自动收拾。** `test:unit` 和 Playwright 每次运行都建一个专属临时根目录（`formicand-run-*`），把 `TMPDIR` 指过去（[test-run-root](../scripts/test-run-root.mjs)）。运行结束时还以这里为数据目录活着的后端会被停掉，并判本次失败。
- **启动了 App 要收尾。** 后端在窗口关闭后会继续运行，所以启动 App 的测试收尾时要调用 [`stopNativeBackend(<桌面数据目录>)`](../test/native-backend-fixture.mjs)。
- **用真实链路。** 生命周期相关的测试要覆盖真实的 Pi hook 顺序和子进程结束，不能只用测试替身。
- **覆盖异步边界。** 归属、取消、迟到的返回、冲突、退出和恢复。协议测试两端都要验证。

## 专项测试

**项目数据，两种引擎。** SQLite 和 PostgreSQL 跑同一组场景：

```sh
docker pull postgres:18.6-alpine3.24
node scripts/test.mjs --skip-build --file test/p3-foundation-integration.test.js
```

没有 Docker 或 PostgreSQL 时这个测试会失败，不会算跳过。只想跑 SQLite 时设置 `FORMICAND_TEST_ENGINES=sqlite`，但合入前要两种都跑。界面流程：`npx playwright test e2e/p3-foundation-flow.spec.js --workers=1`。

**性能。** 先查读取次数、并发请求和 DOM 是否保留，再测耗时：

```sh
node --test test/workspace-directory-performance.test.js test/refresh-performance.test.js test/event-stream-ledger-performance.test.js
npx playwright test e2e/dashboard-polling.spec.js e2e/composer-visibility.spec.js --workers=1
```

比较耗时要保持同样的数据、窗口数、冷热状态和负载。

**打包的 App。** `npm run desktop:pack` 后运行 `npm run test:desktop`。已有候选包时可以直接跑：

```sh
FORMICAND_DESKTOP_APP=.tmp/release/mac-arm64/Formicand.app node scripts/desktop-smoke.mjs
FORMICAND_DESKTOP_APP=.tmp/release/mac-arm64/Formicand.app node scripts/desktop-smoke.mjs --settings-only
```

**原生窗口和输入。** 需要解锁的 Mac 和已经授予的系统权限：`npm run test:release -- --native --stage app`。普通测试入口不跑这些。

**附件解析。** 需要 Python 3.11 和 [document-requirements.txt](../scripts/document-requirements.txt) 里的库，用 `FORMICAND_PYTHON` 指向它。缺库要修环境，不能把跳过当通过。

## 发版验收

`npm run test:release` 按四个环节运行现有的自动测试，保存日志和报告。它不会调用收费模型，也不会申请系统权限。

```sh
npm run test:release -- --list              # 只看计划，不构建不运行
npm run test:release                        # 构建一次，跑全部环节
npm run test:release -- --stage cli         # 只跑一个环节
npm run test:release -- --native            # 加上真实窗口和 Electron 测试（Mac）
npm run test:release -- --native --packages # 同时打出 CLI 包和 DMG，之后人工安装验收
npm run test:release:runner                 # 发版执行器自己的测试
```

| 环节      | 验什么                                         |
| --------- | ---------------------------------------------- |
| 基础功能  | 不经过终端或界面的核心机制                     |
| CLI       | 终端入口、配置、安装、命令和交互               |
| App       | 桌面宿主、会话界面、输入和导航                 |
| 用户 case | 一个完整的用户目标，多项能力组合后交付正确结果 |

报告存在 `.tmp/release-tests/<时间和随机 ID>/`：`report.json` 记录源码提交、环境、命令、每步结果和用例映射；`summary.md` 是摘要和人工待验清单；每步一个日志。

结果分 `passed`、`passed_with_skips`、`failed`、`interrupted`、`incomplete`。退出码 0 是选中的步骤通过，1 是失败或不完整，130 是被中断；加 `--strict` 时证据不完整返回 2。发版验收目前总是显示 INCOMPLETE，因为真实模型、最终安装包和人工体验不会自动验证，要另外记录。

除了自动部分，发版前还要人工核对：

| 范围     | 核对                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| 最终 DMG | 校验 SHA-256，装到没有开发环境的另一台 Mac：首次启动、连接模型、失败恢复、备份和升级 |
| 原生能力 | 窗口访问按系统权限单独验收，实际运行和跳过分开记录                                   |
| 真实模型 | 用自己的服务和预算跑代表性任务                                                       |
| 分发     | 版本、tag、产物、支持平台、签名状态、已知限制和许可证                                |

记录系统、芯片、版本和安装包的校验值。

### 维护用例清单

[catalog.json](../test/release/catalog.json) 保存环节分类规则、用例和测试文件的对应关系，以及人工检查项。发版执行器从本页附录的表格里读用例编号：一级编号如 `BASE-01`，子项如 `GUI-01/permissions`，子项必须有对应的一级编号。

- 新的 Node 测试文件没匹配分类规则时归到基础环节，浏览器测试归到 App 环节。新增领域时补分类规则。
- 加新功能时，先在附录里补用户操作和通过标准，再加测试和对应关系。
- 测试文件通过只算“部分对应”（`partial_mapping`），没有对应测试的是“计划中”（`planned`）。逐条覆盖要人工核对断言。

#### 窗口操作的子项

在候选 App 上用隔离的测试窗口和独立的测试数据逐项操作。G1 是原生测试窗口（姓名、备注输入框，勾选项和保存按钮，基于 `test/fixtures/computer-window.swift`）；G2 是 TextEdit 里新建的纯文本测试文档。

| 子项                  | 操作                                                                      | 通过标准                                                                         |
| --------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| GUI-01/permissions    | 没有系统权限时打开“设置 → 窗口访问”，依次开启屏幕录制、辅助功能、窗口访问 | 每一步告诉用户缺什么、下一步做什么；已给的权限不重复申请；回来后原任务和草稿还在 |
| GUI-01/local-confirm  | 开启窗口访问后重启后端，再打开设置                                        | 显示等待本机确认，不会自动重新开启；确认后恢复                                   |
| GUI-02/observe        | 让 Agent 观察 G1，用户同时查看界面上的预览                                | 截图和控件结构对应 G1；预览不影响 Agent 的观察凭据；不支持图片的模型不假装看图   |
| GUI-02/click          | Agent 观察后点击输入框和勾选项，再观察                                    | 焦点和勾选状态正确；“已发送”和“控件已改变”分开核对                               |
| GUI-02/unicode        | 在姓名和备注里输入中文、组合 Emoji 和多行文字，保存后读回文件             | 内容逐字节一致；长文本不截断；没有输进别的框或 Formicand 的输入框                |
| GUI-02/shortcut       | 全选替换、Tab 切换、Enter 保存                                            | 只作用在目标窗口；最终字段和文件正确；之后还能继续对话                           |
| GUI-02/effect-unknown | 动作发出后截图失败，恢复观察后再继续                                      | 不因观察失败重复输入；已发生的结果保留，保存的内容没有重复                       |
| GUI-03/move           | Agent 观察后用户移动或缩放窗口，再执行旧动作                              | 旧坐标不会误点；提示需要重新观察；重新观察后能继续                               |
| GUI-03/another-window | 同一个应用开 A、B 两个窗口，让 Agent 操作 A，用户切到 B                   | 不会写进 B；能重新选中 A；窗口名相同时也按身份区分                               |
| GUI-03/save-dialog    | 在 G2 未保存的文档上触发保存对话框                                        | 能观察并操作保存对话框，文件保存到测试目录                                       |
| GUI-04/takeover       | 连续操作中点“暂停 · 人工接管”或按 Ctrl+Option+Esc，用户手动改一段         | 排队的动作停止，已发出的如实记录；人工改的内容保留；恢复入口容易找到             |
| GUI-04/pending-grant  | 开启窗口访问的回应很慢时立刻暂停或关闭，再让旧回应到达                    | 不会意外重新开启；状态和用户最后的意图一致                                       |
| GUI-04/task-end       | 运行中分别停止任务、切换工作区、退出 App                                  | 按各自的生命周期停止；重新打开后不会悄悄控制窗口                                 |
| GUI-05/system-block   | 撤销系统权限、锁屏或开启安全输入后尝试观察和操作，再恢复                  | 不乱输入；说明真实原因；恢复后能继续，任务和已保存的结果不丢                     |
| GUI-05/disconnect     | 工具请求中途断开，服务恢复后核对记录再继续                                | 已发出的动作不重复，没发出的停止；授权状态显示准确                               |
| GUI-06/real-app       | 在 G2 新建文档，输入 G1 的内容，保存到测试目录后重新打开                  | 真实软件、保存对话框和文件结果都正确；测试窗口通过不能代替这一项                 |
