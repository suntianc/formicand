# CoworkOS 桌面会话 CPU 与内存分析报告

2026-11-22 · macOS 开发版 · 现场采样与隔离实验，优化方案待实施

**建议先改工作状态动画，再改工具历史的加载方式。** 真实窗口中，渲染进程和 GPU 辅助进程合计占用约 2 GB。隔离实验确认了两项可以分别优化的开销：等待时循环动画持续占用 CPU，打开会话时页面提前持有折叠工具结果的全文。真实窗口 2.7 GB 的历史峰值仍需单独归因。

## 一、真实桌面现场

在一台 10 个逻辑核心、32 GB 内存的 Mac 上，保持现有会话运行。用 `ps` 在约 24 秒内采集 13 次 CPU 读数，用 `top` 在约 104 秒内采集 10 次进程内存，用 `vmmap -summary` 核对渲染进程的物理内存占用及峰值。

| 进程            | 平均 CPU | 最后一次内存采样 |
| --------------- | -------: | ---------------: |
| 窗口渲染进程    |      84% |        1,562 MiB |
| GPU 辅助进程    |      31% |          483 MiB |
| Electron 主进程 |      13% |          142 MiB |
| 后台服务        |       3% |          153 MiB |

CPU 的 100% 对应一个逻辑核心。GPU 辅助进程一栏计量的是该进程消耗的 CPU。前两项内存合计 2,045 MiB，另有主进程、后台和 Agent 各自的开销。

渲染进程的内存从 1,612 MiB 开始，中间一度回落至 1,535 MiB，最后为 1,562 MiB。`vmmap` 记录的进程生命周期峰值为 2.7 GiB。这段采样里内存有升有降，尚未取得峰值时的对象引用链，内存泄漏仍待验证。

## 二、CPU：等待期间的状态动画

小蚂蚁的 SVG 部件分别缩放并改变透明度，“思考中”的文字通过移动渐变背景产生扫光，两种动画都无限循环。用独立 Chromium 窗口打开同一段 20 轮合成会话，让本地假模型保持请求打开、不发送新文字。每种状态稳定后，测量约 3.5 秒内的进程 CPU 时间。下表汇总数次对照实验的读数。[动画样式](../web/assets/styles/conversation.css) · [会话测试夹具](../e2e/perf/fixture.js)

| 等待期间的界面                 | 渲染进程 CPU | GPU 辅助进程 CPU |
| ------------------------------ | -----------: | ---------------: |
| 小蚂蚁和文字扫光持续播放       |     20%～24% |         88%～97% |
| 只暂停文字扫光                 |           4% |              97% |
| 只暂停小蚂蚁                   |           6% |              97% |
| 全部暂停                       |           1% |               8% |
| 换成一个持续呼吸的圆点         |           3% |         84%～87% |
| 状态变化时闪动两下，结束后静止 |           2% |           7%～9% |

恢复原动画后，渲染进程重新升至 26%，GPU 辅助进程升至 95%。减少动画元素能降低渲染进程开销；结束持续播放才能同时降低两个进程的开销。隔离窗口复现了其中一个原因，现场渲染进程平均 84% 的其余开销尚未分解。

**建议改法。** 保留小蚂蚁和状态文字，取消持续扫光。首次进入“思考中”时，图标短暂闪动，随后静止；进入“等待子代理”时显示静态等待状态。动画绑定到工作状态转换，同一状态内收到 token、轮询返回或 DOM 更新时沿用已有状态。开启“减少动态效果”时直接显示静态图标。文字输出、计时和子代理完成通知照常更新。

## 三、内存：折叠的工具历史

从一个运行中任务的持久化历史按现有代码重建，整理出了 3,324 条事件，序列化后约 7.0 MB。仅 312 条工具结束事件就占 5.1 MB，约占 73%。打开会话时，详情携带工具结果。渲染“处理过程”时，即使条目折叠，前端也会生成工具参数、返回结果和相应 DOM。[事件投影](../src/runtime/conversation-history.ts) · [会话详情](../src/dashboard/task-conversation-service.ts) · [处理过程渲染](../web/assets/controllers/conversation-activity-view.js)

用本地假模型构造 40 轮、320 次工具调用的历史，在独立页面比较四种实现。摘要实验用短文本代表可按需获取的完整结果。页面打开后主动回收垃圾，再测 JavaScript 已用堆和 DOM 节点数。

| 页面打开时的处理方式       |  详情响应 | 回收后 JS 堆 | DOM 节点 |
| -------------------------- | --------: | -----------: | -------: |
| 当前实现                   | 11.19 MiB |     31.7 MiB |   20,544 |
| 只传工具摘要               |  1.56 MiB |      8.6 MiB |   20,544 |
| 只延迟生成折叠内容         | 11.19 MiB |     26.6 MiB |    6,784 |
| 工具摘要和延迟生成同时启用 |  1.56 MiB |      7.6 MiB |    6,784 |

**先缩小响应，再延迟渲染。** 两项合用时，这组数据的详情响应缩小约 86%，回收后 JS 堆下降约 76%，DOM 节点减少约 67%。另一组 20 轮长文本对照中，两次从长会话切回空会话并回收垃圾后，JS 堆分别从 10.4 降至 3.8 MiB、从 10.2 降至 4.0 MiB。单纯切换长文本会话未复现现场峰值。

**建议改法。**

1. 会话详情和实时事件共用工具摘要。展示所需字段包括工具名称、状态、简短结果、错误摘要和稳定的结果标识；进行中的步骤继续显示进度。
2. 展开“处理过程”时生成步骤列表；展开某次工具调用时，按任务、Run 和事件标识读取对应参数与完整输出。复用现有持久化记录，确保旧会话也能展开、复制和查看失败详情。[实时事件入口](../src/dashboard/event-stream.ts)
3. 全文绑定到当前会话。切换会话后释放正文及相关 DOM，并丢弃已切走会话的迟到响应。折叠、焦点和滚动位置沿用现有交互。

## 四、实施顺序与验收

| 顺序                  | 验收场景                                                                                   | 判断标准                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 调整动画           | 同机、同窗口尺寸，对比静态空闲、无输出思考、等待子代理和恢复输出；每种状态稳定后采样 30 秒 | 短反馈结束后循环动画数为零，等待时两个进程的平均 CPU 接近同窗口静态基线。连续 token 不重启动画，等待标签保持正确。                                             |
| 2. 工具摘要与延迟渲染 | 用同一份 40 轮、320 次调用的历史比较前后版本，再展开、复制、折叠并切换会话                 | 响应大小、回收后堆和 DOM 同时下降，以本报告原型读数作对照。展开取得完整结果，旧会话、失败工具和实时完成的工具均可查看。                                        |
| 3. 复验真实桌面       | 在同一份长会话上重复“打开、输出、等待、切走、重新打开”，记录每轮相同位置的进程内存和 JS 堆 | 分开观察峰值和切走后的基线。若基线逐轮抬升，在固定检查点对比堆快照，用保留大小和引用链定位持有者；若 JS 堆回落而进程物理内存持续升高，转查原生分配和图形资源。 |

先通过独立浏览器的同负载对照，再在实际 Electron 窗口复测。最终以桌面等待时的 CPU、重复使用后的内存走势，以及工具历史仍可完整访问作为交付依据。
