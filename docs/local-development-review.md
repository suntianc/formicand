## 项目、会话与需求台账

### 01 · 高 · 合并需求会丢失来源需求的新修订

读取来源和目标需求后，另一位操作者把来源描述从修订 1 改为 2。按旧描述提交合并仍然成功，来源查询返回 `not_found`，目标也没有保留新描述。合并服务只比对保留方的修订号。[需求合并实现](../src/workspace/project-data-service.ts)

**验收**：合并双方中任一方在读取后发生修订，旧请求都应返回冲突，双方记录和修订历史均可读取。重新读取双方后可完成合并。

**9882b081 复验（已通过）**　通过远程客户端提交合并，缺少来源修订号会被拒绝，来源或目标修订过期均返回冲突，双方的修订历史保留。重新读取双方修订号后合并成功。

### 02 · 高 · 并发列举会话会改变新会话的类型和需求归属

创建绑定需求的 `continuation` 会话，在本地 Task 已写入、共享会话尚未写入时请求会话列表。列表把 Task 作为旧数据收养，创建接口最终返回 `regular`，且丢失 `requirementId`。同一写入顺序还会留下无效请求的副作用：在空项目中提交 121 字标题，接口返回 HTTP 400，随后列举却出现了新会话。[创建与收养](../src/dashboard/main-session-service.ts) · [共享会话存储](../src/workspace/project-data-service.ts)

**验收**：在两次写入之间并发列举，创建响应和随后列举都保留请求的会话类型、需求和唯一身份。无效标题返回 400 后，Task 和会话数量均不增加。既有旧版 Task 仍能正常收养。

**本地修复复验（已通过）**　对真实 Dashboard 注入一次 `task.created` 写入错误，在事件写入处暂停并并发列举，得到的会话仍绑定原需求；释放写入后创建返回 HTTP 400，随即列举得到空列表。按原参数重试返回 201，列表只有一条本地 `continuation`，保留原需求 ID。新建项目 Task 在暂存目录写完初始事件后才对外可见。[项目 Task 回归](../test/project-catalog.test.js)

**验收**：在同一台账中，“CSV导出”“CSV 导出”“导出CSV”都能召回该功能，原有中文和英文检索用例通过。

## 开发记录、票与 Git 工作现场

### 04 · 高 · 一张票检查失败会回滚另一张已并入的票

对同一需求并行执行两次 `integrate_ticket`。票 A 并入后暂缓检查，票 B 并入、通过检查并记为 `merged`，再让 A 检查失败。A 的回滚把需求现场恢复到两张票并入之前，B 的文件消失，台账仍显示 B 已并入。[并票、检查与回滚](../src/dashboard/project-development-service.ts)

**验收**：用相同交错顺序验证，失败操作只能撤销自己的改动。每张 `merged` 票的集成提交都在需求分支历史中，对应文件仍可读取；重试 A 后结论一致。

**本地修复复验（已通过）**　两个独立进程共享 SQLite 和 Git 现场，A 检查失败后，B 的文件和已记账提交均保留。强制终止 A 后先并 B，再重试并让 A 失败，B 的提交未带入 A 的文件。并票与回滚由同一工作树锁串行处理。[并票回归](../test/p48-ticket-flow.test.js)

### 05 · 中 · 中文文件名在票范围检查和文档登记中被误判

使用默认 Git 配置，票明确允许修改 `docs/使用说明.md`，冻结时仍报 `ticket_scope_exceeded`。Git 输出的引号及转义字节被当作文件名的一部分。文档枚举也受影响：新增的中文 Markdown 可以漏过登记，正确登记后又被判为路径失效。[工作区路径枚举](../src/workspace/development-workspace.ts) · [票范围检查](../src/dashboard/project-development-service.ts)

**验收**：允许范围内的中文路径可送审，范围外的路径仍被拒绝；中文 Markdown 未登记时被指出，登记后可冻结。检查使用 Git 原始路径，不依赖用户修改 `core.quotePath`。

**本地修复复验（已通过）**　送审及并票按改名的来源和目标分别核对票范围。真实 Git 测试覆盖从范围外移入、从范围内移出和范围内改名，前两种被拒绝并保留原文件，第三种顺利合入。含中文和双引号的目标路径也通过了检查。[票范围回归](../test/p48-ticket-flow.test.js)

## 固定候选审查与返修

### 07 · 高 · 终审失败的同一提交可以再次冻结并取得交付资格

完整路线首轮终审失败，且没有单独待裁定的阻塞发现。对原 SHA 发起复审时，带上前次 `previousReviewId` 会收到 `review_candidate_unchanged`，省略它却能新开终审。第二位 Reviewer 判通过后，服务返回 `eligible: true`，期间没有修复票或新提交。[终审冻结与交付资格](../src/dashboard/project-development-service.ts) · [返修流程](../src/domain/development-ticket.ts)

**验收**：服务根据持久化审查记录确定上一轮。对失败的原候选，无论是否填写前次 ID，交付资格都保持关闭；修复票并入新候选并通过关联复审后才开放。

**9882b081 复验（已通过）**　对首轮失败的原 SHA，填写或省略 `previousReviewId` 都会被拒绝，交付资格保持关闭。并入修复票后，新候选自动关联失败轮次，通过复审后才取得资格。

### 08 · 中 · 同一候选可以产生两份进行中的整体终审

对同一已并完全部票的候选，同时发出两次冻结请求。两次都成功，产生两个不同的审查 ID，状态均为 `in_review`。开放轮次检查与创建记录分属不同操作。[终审检查](../src/dashboard/project-development-service.ts) · [审查写入](../src/workspace/project-data-service.ts)

**验收**：并发冻结后，存储中只有一份开放终审。调用方收到同一记录或明确的冲突；后续裁定和交付判断引用唯一的审查记录。

**本地修复复验（已通过）**　两个独立进程同时冻结同一候选，共享存储只出现一条 `in_review`。直接向 PostgreSQL 18 并发提交四次，数据库事务接受一次，其余三次返回 `review_open`。[终审冻结回归](../test/final-review-mapping.test.js)

## 合入、交付与文档登记

### 09 · 高 · 发布期间切换工作树分支，会更新错误分支并报告成功

在临时 Git 仓库中，服务已定位检出 `main` 的工作树，在执行快进前把该工作树切换到 `other`。真实 Git 操作推进了 `other`，`main` 仍在原提交，`publishMerge` 却返回 `updated`，上层按成功结果进入交付记账。[Git 发布](../src/workspace/project-merge.ts) · [交付记账](../src/dashboard/project-development-service.ts)

**验收**：重现同一切换时序，`other` 保持原提交。只有目标分支包含预期合入提交时才允许成功回执和交付记账；无法安全更新时保留可重试状态。

**本地修复复验（已通过）**　发布时由 Git 引用事务锁住 HEAD 和对应分支，核对目标后再更新工作树并提交事务。定位目标后连续两次切换分支，发布返回 `blocked`，三个分支均保留原提交；另一分支此前已合法快进到候选时，其 reflog 也保持原样。正常发布保留无关的暂存及未暂存改动，遇到会被覆盖的文件则拒绝发布。在工作树已更新而引用尚未提交的状态下重试，目标分支与工作树均恢复一致。[发布竞态回归](../test/project-merge-publish.test.js) · [合入恢复回归](../test/p4-integration-recovery.test.js)

**同时操作同一工作树**　在 Git 2.52 的实测中，发布已经锁住目标分支时，另一条 `git switch` 因 `HEAD.lock` 失败。这条切换命令在报错前已将另一个分支的一处文件差异写入暂存区。发布成功，两个分支的 SHA 均正确，`git status` 仍显示该差异。

### 10 · 中 · 历史失效的文档登记阻断无关需求终审

基线登记表已有失效条目 `old.md`。本次需求仅新增 `feature.js`，冻结终审仍报 `documents_unregistered`，要求开修复票处理旧条目。已有登记表时，规格约定检查本需求带来的问题。[增量检查约定](workloop-comparison.md) · [冻结前检查](../src/dashboard/project-development-service.ts)

**验收**：仅修改业务代码时，基线既有的失效条目不阻塞终审；如果本次删除已登记文件却保留登记，仍须拒绝冻结并指出路径。首次建表仍检查全部文档。

**9882b081 复验（已通过）**　基线已失效的 `old.md` 不再阻断纯业务改动。本次删除仍在登记表内的 `docs/guide.md` 会拒绝冻结并指出路径；首次建表检查全部文档的用例通过。

### 11 · 中 · 维护快照之后的新合入会从下一轮清单消失

维护开始时读到 0 项，提交结论前发生 1 项合入，此时重新读取能看到该项。从原快照提交维护结论后，下轮计数和变更清单都回到 0。游标使用提交结论时的时间，跨过了本轮实际读过的边界。[维护读取与完成](../src/workspace/project-data-service.ts)

**验收**：按同一顺序插入一次合入，本轮提交旧快照的结论后，下轮能看到这项合入及其历史。完成覆盖它的维护后，才从待维护清单移除。

**本地修复复验（已通过）**　PostgreSQL 18 并发完成新旧快照，旧快照返回 `tidy_stale`，持久游标保留新值。固定系统时间，在快照后写入两笔交付，下一轮有两条历史、计数为 2，完成该轮后计数归零。开发状态的合入计数使用只读查询。v13 升级时，与旧游标同毫秒的记录会重新列出一次；升级前打开的维护快照需要重新读取。[交付回归](../test/p4-delivery-records.test.js) · [迁移回归](../test/p8-ledger-tidy.test.js)

### 13 · 中 · 克隆服务停止时没有等待项目注册完成

用本地 Git 仓库完成克隆并暂缓注册响应，调用 `stop()`。停止调用已返回时，记录仍为 `registering`；释放响应后才变成 `completed`。服务在注册前就移走运行记录，停机时等待不到它。[克隆注册与停机](../src/dashboard/project-clone-service.ts)

**验收**：注册仍在进行时调用停止，只有在注册结果和终态持久化后才返回；再次启动服务能读到一致的项目和克隆记录。

**本地修复复验（已通过）**　分别在克隆终态写入失败前后调用 `stop()`，两次都向调用方报告写入错误。恢复存储并重启，原记录恢复为 `completed`。[克隆停止与恢复回归](../test/p45-project-clone.test.js)
