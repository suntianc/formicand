# 上下文检索增强设计（P8）

状态：2026-11-21 草案，待用户确认。阶段位置见 [开发阶段规划](development-phases.md#p8上下文检索增强)。

## 一、要解决什么

Main 做新需求时，要守住项目以前定下的规矩：某个格式、某个命名、某条兼容要求，以及哪条旧决定已经推翻。按 [记忆与上下文压缩设计](memory-and-compaction-design.md#会话笔记记忆记录怎么分工) 的分工，这些记在需求台账里。现在的问题是 Main 不一定去查，查了也不一定查得到。

### 测出来的缺口

测评任务 `history`（老项目）：台账里预先放 25 条需求，其中 6 条带着这次要守的规矩，其中一条旧决定已被推翻。提示只说“按我们之前定下的规矩来”。`history-large` 把同样的规矩埋在 150 条需求的最早一批里。任务说明见 [测评说明](../scripts/eval/README.md)。

| 版本     | 任务           | 结果 | 查台账 | 说明                                                                                                           |
| -------- | -------------- | ---- | ------ | -------------------------------------------------------------------------------------------------------------- |
| 现有台账 | 老项目 #1      | 通过 | 5      | 走开发流程，按工具说明先查重；不带关键字一次拿到全部 25 条，规矩都在里面                                       |
| 现有台账 | 老项目 #2      | 未过 | 0      | 当小改动直接改代码，只翻了记忆和会话历史，汇报“没找到任何成文记录”，字段名自起                                 |
| 现有台账 | 老项目（大）#1 | 未过 | 1      | 不带关键字查了一次，拿到最近 50 条，规矩一条不在；只看到“日期相关的展示：讨论后没有定论”，就问用户，再自定格式 |
| 现有台账 | 老项目（大）#2 | 未过 | 1      | 同样只查一次；把无关的“输出保持英文”“列顺序保持现状”当成规矩，日期存成完整时间戳                               |

归纳为三个缺口：

1. **不知道去哪找。** Main 的工作守则里没提台账；它只在走开发流程、按工具说明“新建前先查重”时顺带查到。查不查看走哪条路。
2. **搜不到决定。** 关键字只匹配需求的标题和正文，不匹配决定原文。“创建日期”“created”都搜不到“字段命名”那条，虽然词就写在它的决定里。多个词要整段连着出现才算命中。
3. **规模一大就靠不住**（大项目两次都栽在这里）。 不带关键字时返回最近更新的 50 条。150 条时最早的规矩一条都不在里面（每次约 2.2 万字符）；按“日期”“导出”搜，每次十几条里只有一两条相关。

另外，平时没有地方提醒 Main 往台账里记决定：工作守则和开发技能都没提，只有工具说明里一句“decide 记录已定的决定”。不补上这一头，真实项目的台账里不会有可查的规矩。

## 二、好产品怎么做

| 做法                         | 谁在用                                                                                                                                                  | 要点                                                                                                                               |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 开头直接放进上下文           | Claude Code 的 CLAUDE.md；Codex 的 AGENTS.md（合计默认上限 32 KiB，超出的截掉）                                                                         | 少而稳定的规矩每次都在，不靠模型想起来去查                                                                                         |
| 用到时再查                   | Claude Code 用 grep、glob 现查文件，放弃了向量索引；Codex 同样                                                                                          | 没有会过期的索引；代价是多几次工具调用                                                                                             |
| 两者结合                     | Anthropic 的上下文工程文章                                                                                                                              | 开头放一小份，其余按需查；只放能定位内容的短标识                                                                                   |
| 按说明决定要不要取           | Cursor 规则的“由智能体决定”类型、Devin 的 Knowledge（按触发描述取用，现改为技能）                                                                       | 每条带一句说明，模型看说明决定是否取全文                                                                                           |
| 决定记录保留历史、只列生效的 | 架构决定记录（ADR）的常见做法                                                                                                                           | 推翻的记录不删，标“已被某条取代”；给智能体的入口是“现在生效的决定”清单，旧的只作历史                                               |
| 检索工具怎么写               | Anthropic《为智能体写工具》                                                                                                                             | 围绕任务合并成少数工具；返回有意义的内容而不是底层编号；默认条数和截断要克制，结果太多时提示改用更小更准的查询；可选精简或详细返回 |
| 中文全文索引                 | SQLite FTS5 默认分词不切中文，`trigram` 分词要求至少 3 个字，2 个字的中文词查不到；PostgreSQL `pg_trgm` 按 3 字节切，对中文基本无效，社区建议 `pg_bigm` | 两种存储都没有现成好用的中文索引；在几千条以内，按项目逐行做子串匹配已经够快，中文也天然可用                                       |

来源：[Anthropic：上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[Anthropic：为智能体写工具](https://www.anthropic.com/engineering/writing-tools-for-agents)、[Codex：AGENTS.md](https://developers.openai.com/codex/guides/agents-md)、[Cursor：规则](https://cursor.com/docs/context/rules)、[Devin：Knowledge](https://docs.devin.ai/product-guides/knowledge)、[O'Reilly：编码智能体与决定记录](https://oreilly.com/radar/coding-agents-love-decision-records/)、[SQLite FTS5](https://sqlite.org/fts5.html)、[PostgreSQL 邮件列表：pg_trgm 与中文](https://www.postgresql.org/message-id/2533.1568132505%40sss.pgh.pa.us)。Claude Code 放弃向量索引一事来自其负责人的公开访谈，见 [转述](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/)。

结论：照 Claude Code 和 Anthropic 的思路，**开头放一份“现在生效的决定”，其余用到时搜**；搜索沿用子串匹配，先把搜的范围和返回的内容做对，不上向量和全文索引。

## 三、设计

### 1. 开头放生效决定清单

- 每次请求在系统提示里放 `project_decisions` 一节，与记忆索引并列。内容是本项目**仍然生效**的决定，每条一行：`需求标题：决定原文`，最近的在前。已推翻的不列。
- 上限 8000 字符。放不下时只列最近的，末尾写“还有 N 条较早的生效决定”。不教怎么查，查法在工具说明里。
- 没有任何决定时整节不出现。
- 子代理不自动获得，由 Main 在派单时把相关的规矩写进任务，和记忆的处理一致。

效果：缺口 1 在中小项目里直接消失，规矩每次都在眼前；大项目至少能看到最近的规矩，并知道还有更多。

### 2. 搜索

`project_ledger` 的 `query` 改为：

- **搜的范围**：需求标题、正文和全部决定原文（含已推翻的）。
- **多个词**：按空白拆开，任何一个词命中就算，按命中的词数排序，词数相同时最近的在前。模型可以一次给几个同义词和英文名，例如 `创建日期 created 日期 导出`。
- **返回什么**：每条需求只返回标题、状态、命中的那几条决定（标明生效或已推翻、被哪条取代）、正文里命中处前后的一小段，以及最近一次交付的合入提交号。不带全部正文和所有决定，要看全文用 `get`。
- **默认 20 条**，最多 50 条。命中更多时说明总数，并提示换更准的词。
- 不带关键字时行为不变，仍按最近更新列出，供查重和浏览。

工具说明补一句：台账里有项目以前定下的需求和决定；用户提到“之前定的”“老规矩”，或要改的东西以前可能定过时，先搜。

### 3. 推翻与取代

- `decide` 增加可选参数 `supersedes`（被取代的决定编号）。记下新决定的同时把旧的设为不生效，并记下取代关系。
- 搜索结果里，已推翻的决定显示“已被取代：<新决定的需求标题>”，清单里不再出现。

### 4. 什么时候记决定

- 工具说明与开发技能各加一句：用户定下或确认了**产品应该怎样表现**的规矩（格式、命名、兼容、明确不做的事），记在它所属的需求上；改主意时用 `supersedes` 取代旧的，不改写旧文字。
- 与其他地方的分工不变：怎么跟用户合作（习惯、偏好、纠正）记在记忆；仓库里的构建和测试约定写在 AGENTS.md；当前需求的完成标准写在开发记录。

### 5. 不做的

- 向量检索：Claude Code 已经放弃；需要额外的嵌入模型，索引会过期，中文效果依赖模型；按项目算条数也不多。
- 全文索引（FTS5、`pg_trgm`）：对中文都不好用（见上表）。等测出慢了再加，届时优先考虑二字切分。
- 跨会话搜原话：`search_history` 仍只查当前会话。有了生效决定清单以后，看测评是否还需要。
- Turso 仍是候选，不在本阶段采用。

## 四、验证

- 存储层：SQLite 与 PostgreSQL 跑同一组用例：多词命中与排序、搜到决定原文、命中片段、取代关系、默认与上限条数、清单上限与截断。
- Main 进程：生效决定清单进入系统提示，推翻后消失，子代理拿不到。
- 测评：`history` 与 `history-large` 各跑 3 次，对比改动前后：是否通过、查台账几次、用了多少 token。另抽查一次普通任务（如 `due`），确认清单不影响无关任务。

## 五、步骤

1. 搜索：范围、多词、返回内容、条数、交付提交号。
2. 取代关系：`supersedes`。
3. 生效决定清单进入系统提示。
4. 工具说明与开发技能：何时搜、何时记。
5. 测评对比，结果写回本文档。

每步测试通过后合入。
