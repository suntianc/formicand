# 上下文检索增强设计（P8）

状态：2026-11-22 第三稿，用户已确认方向，暂未开始实施。第二稿照 workloop 的需求台账定了方向；第三稿按现有代码细化，并记下用户的三条决定：归属由 Main 自行判断，不找用户确认；与长期功能无关的改动归到每个项目自带的“杂项”需求；测评用 DeepSeek 跑真实模型。阶段位置见 [开发阶段规划](development-phases.md#p8上下文检索增强)。

第一稿是凭调研文章推出来的，用户指出应该照已经在真实项目里用起来的做法来。本稿以 workloop 的需求台账技能为参考：它在 change-bot 项目上用了一个月，台账里 17 条需求，覆盖了全部开发。参考的原样拷贝在 [vendor/workloop-skills](../vendor/workloop-skills/SOURCE.md)，主要读的是 `requirement-ledger`、`paseo-workloop` 和 `domain-modeling` 三个技能。

## 一、要解决什么

用户提新需求时，Main 要知道这块功能以前做过什么、当时定了什么，再在这个基础上改，不推翻用户已经认可的东西。

### 第一轮测评暴露的问题

测评任务 `history`（25 条需求）和 `history-large`（150 条需求），提示只说“按我们之前定下的规矩来”。任务说明见 [测评说明](../scripts/eval/README.md)。

| 任务           | 结果 | 查台账 | 说明                                                         |
| -------------- | ---- | ------ | ------------------------------------------------------------ |
| 老项目 #1      | 通过 | 5      | 走开发流程顺带查重，不带关键字一次拿到全部 25 条             |
| 老项目 #2      | 未过 | 0      | 当小改动直接改，没查台账，字段名自起                         |
| 老项目（大）#1 | 未过 | 1      | 不带关键字只拿到最近 50 条，规矩不在其中，问了用户后自定格式 |
| 老项目（大）#2 | 未过 | 1      | 同样只查一次，把无关决定当成规矩                             |

对照参考做法以后，这组测评本身的前提也有问题：它照我们现在的模型造数据，**一次请求一条需求**，于是台账越积越多，每条规矩散在不同的需求下面。真实项目按参考做法，同样的历史只有十来条需求。所以测评要重做（见第五节），上表只作为“现在的模型规模一大就不行”的证据。

## 二、参考做法：workloop 的需求台账

### 1. 一条需求是一块长期功能

需求是“用户登录”这样能被多次交付的长期功能；“给登录加验证码”是归到它下面的一次工作。一次开发（run）只属于一条需求，一条需求有很多次开发。change-bot 整个项目只有 17 条需求，例如“智能评审与 AI 预审”“变更工单与状态机”“认证、人员与权限”。

### 2. 每条需求有一段一直更新的现状

记录分两部分：

- **人写的**：标题、别名、正文（现状 Summary、按日期的历史 History、备注 Notes）、指针（相关架构决定、踩坑记录、设计文档、代码目录和函数名）。
- **程序写的**：编号、状态、每次开发的交付（提交号、交付时间、归档时间、证据目录、被推翻的旧交付）、小改动的结果（日期、做了什么、提交号、怎么验证的）。

现状里直接写着这块功能该怎样表现，例如“隐患查询失败或没配置时，不能显示成没有隐患”。看现状就知道现在的规矩，不用逐条判断旧决定还算不算数。

台账**只放指针，不抄原文**：设计文档、架构决定、复盘的正文都留在原处。

### 3. 规矩分四处放

| 放什么                                   | 放哪                                      | 谁来读                   |
| ---------------------------------------- | ----------------------------------------- | ------------------------ |
| 某块功能现在怎样表现                     | 台账里这条需求的现状                      | 做这块功能前查到它       |
| 难以回头、不看背景会奇怪、确有取舍的决定 | 仓库 `docs/adr/` 的架构决定，一个决定一份 | 开工前读与要改区域相关的 |
| 领域用词                                 | 仓库 `GLOSSARY.md`                        | 开工前读                 |
| 全项目都要守的工程约定                   | 仓库 `AGENTS.md`                          | 每次都在上下文里         |

架构决定被推翻时：写新的，删掉旧文件，在 `docs/adr-history.md` 里加一行“被哪条取代、原文用哪个提交读”。`docs/adr/` 里只剩生效的；历史表只给人追溯，不约束实现。

### 4. 查找：先找归属，找不准就列全部

用户一提需求，Main 先用用户原话查“这是哪条需求”：

- 搜标题、别名、现状正文和指针；标题和别名权重 1，正文和指针 0.6。
- 英文按词比；中文按两字一组比，单个字算半分。不用分词库，不用模型打分。
- 返回最多 5 个候选，带分数和命中的词，并给一个判断：**很可能是这条**（最高分过 0.5，且是第二名的两倍以上）、**几条都像**、**都不像**。
- 后两种情况下，**附上全部需求的目录**（编号、状态、标题、别名、现状开头 100 字）。条数少，全列出来也不长，由 Main 结合对话判断，判断不了再问用户，最多列三条给用户选。
- 用户确认“我说的 XX 就是这条”以后，把用户的说法加进别名，下次就能搜到。Main 不能自己猜着加别名，猜错了下次会变成错误的强匹配。

### 5. 设计前取上下文

确定归属后，对这条需求取一次上下文，一次拿回：现状和最近的变化、历次开发的设计文档和验收结果、相关架构决定（失效的标出来）、交付提交号和证据目录、代码位置提示。复盘、踩坑和完整历史按需再加。

### 6. 什么时候写

| 时机                       | 做什么                                     |
| -------------------------- | ------------------------------------------ |
| 新功能块                   | 新建需求，带别名                           |
| 用户重新说明这块功能管什么 | 改正文，记一笔备注                         |
| 开发开始                   | 把这次开发挂到需求下                       |
| 开发完成、归档             | 各同步一次交付结果                         |
| 小改动，没有走开发流程     | 记一条结果（做了什么、提交号、怎么验证）   |
| 讨论中定下难以回头的决定   | 写架构决定，与本次开发的第一个提交一起合入 |

参考做法第一版明确不做：父子需求、需求之间的推翻和依赖关系、图。

## 三、我们现在和参考做法的差别

| 方面       | 参考做法                                       | 我们现在                                                   |
| ---------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 需求的粒度 | 长期功能，一条需求多次开发                     | 每次请求一条需求，数据库限定一条需求只能有一条开发记录     |
| 规矩在哪   | 需求现状 + 仓库里的架构决定、用词表、AGENTS.md | 挂在需求下的一条条决定，靠“是否生效”区分                   |
| 别名       | 有，用户确认后才加                             | 没有                                                       |
| 查找       | 两字一组打分，分三档，找不准列全部目录         | 标题和正文整段字面匹配，不搜决定，不带关键字时给最近 50 条 |
| 取上下文   | 一次拿回现状和所有指针                         | 只有逐条 `get`                                             |
| 小改动     | 记一条结果，挂在需求上                         | 小改动也建一条需求、一条开发记录                           |
| 提示 Main  | 主流程写明“先查再澄清”                         | Main 的工作守则不提台账，只在开发技能里“新建前先查重”      |

## 四、设计

照参考做法改，不另起新花样。与参考做法不同的地方都写明了原因。

### 1. 需求改成长期功能

- **一条需求挂多条开发记录**：去掉数据库里“一条需求只能有一条开发记录”的限定。同一时间最多一条在进行中，避免两次开发同时改同一块功能；新开发要等上一条合入或撤回。
- **内容分三块**：
  - 现状：这块功能现在的样子和规矩，每次交付后更新；
  - 历史：按日期一行一条，写哪次开发改了什么；
  - 别名：用户对这块功能的其他叫法。
- **状态改为“在用”和“停用”**：“已交付”是一次开发的结果，挪到开发记录上，不再挂在需求上。
- **去掉“决定”**：规矩写进现状；难以回头的写成仓库里的架构决定（`docs/adr/`），执行者和审查者开工时都读得到。
- **杂项需求**：每个项目自带一条“杂项”长期需求，与任何长期功能都无关的改动（改错别字、调一个配置）挂在它下面，照常走开发记录和合入。它的现状只写这类改动共同要守的规矩，可以为空。
- **看板改成一次工作一张卡**：同一条需求先后可以有多张卡，同一时间最多一张在进行中；交付回执记在卡上。
- **数据迁移**：数据库升一个版本。原正文放进现状；生效的决定追加到现状末尾；被推翻的决定写进历史，注明被哪条取代；每个项目补一条杂项需求。

### 2. 按原话查找：`lookup`

`project_ledger` 加 `lookup`。打分在参考做法上按调研（第六节）改一处：两字一组的词按 BM25 计分，即越多需求都有的词（“功能”“支持”）分越低，避免常见词把不相关的需求顶上来。

- 搜标题、别名、现状和历史；标题和别名权重 1，现状和历史 0.6；
- 英文按词，中文按两字一组，单个字算半分；不用分词库，不用模型打分，不建索引，每次在内存里算，台账一改就生效；
- 返回最多 5 个候选，带分数和命中的词，并给出三档判断：很可能是这条、几条都像、都不像；
- 后两档附上全部需求的目录：编号、状态、标题、别名、现状开头 100 字；需求不超过 30 条时，第一档也附上，由 Main 再看一眼有没有说法不同的更合适的。

原来的 `query` 只留浏览和按状态筛选。

**归属由 Main 自己判断，不找用户确认**（与参考做法不同：用户不会回答“你说的是哪条”）。三档的处理：

- 很可能是这条：直接用；
- 几条都像：Main 结合对话和目录选一条；
- 都不像：从目录里找意思相同、说法不同的；确实没有就新建需求，与任何长期功能都无关的归到杂项。

**别名由程序在开发开始时加**：Main 新建开发记录时传入用户的原话；它在这条需求上落在“几条都像”或“都不像”时，程序把原话里没命中的说法记成别名，并记下来自哪次开发。这样下次用户换同一种说法就能直接命中。别名记错了可以删除，删除时连同来源一起显示。

### 3. 取上下文：`context`

给一条需求，一次返回：

- 现状和最近 10 行历史；
- 历次开发的目标、完成标准、合入提交和交付时间；
- 现状与历史里提到的架构决定，并检查文件还在不在，不在的标为已失效；
- 代码位置提示：历次开发改过最多的目录。

### 4. 合入时更新现状

- 需求的最后一次合入申请必须带上新的现状和本次历史的一行，不带就拒绝，做法和复盘一样。
- 合入成功后，程序写回台账。合入没成功，台账保持原样。
- 现状没有变化时也要写明“现状不变”和理由。

### 5. 提示 Main

- `task-routing` 和开发技能加一段：用户提开发类请求时，先用原话 `lookup`，定下归属后 `context`，再开始澄清和设计；继续已有需求，不重复新建。
- 讨论中定下难以回头的决定时，写成架构决定，随本次开发的第一个提交合入。
- 记忆的分工不变：怎么和用户合作记在记忆；产品现在的样子记在台账；工程约定写在 AGENTS.md。

### 6. 台账维护

Main 判断归属会出错，把属于已有功能的请求新建成一条需求。这类重复不用每次开发完都查，定期合并一次：

- **何时做**：程序记着上次维护以来新建了几条需求；满 5 条后，下一次合入完成时，`next` 让 Main 做一次台账维护。没有新建需求就不触发。
- **找哪些**：程序把需求两两按同样的打分比一遍，列出相似的几对给 Main，并附全部目录；Main 也可以从目录里找程序没列出的。
- **怎么合**：`merge_requirements` 把一条并入另一条：开发记录、看板卡、交付记录、别名和历史都挪过去，被并的标题变成别名，现状由 Main 写成合并后的样子；挪完后被并的需求整条删除，不留空壳。开发、交付和历史记录本身一条不少。
- **规则**：被并入的一条必须保留原来两条的全部规矩；拿不准是不是同一块功能就不合。
- **全自动**：和复盘一样，不找用户确认，也不在汇报里列出。维护完记下时间和新建计数清零。

### 7. 界面

需求面板改为显示现状、历史和别名，以及这条需求下的历次开发；去掉“决定”。

### 8. 不做的

- 向量检索、全文索引：见第六节调研。
- 图、需求间的关系：参考做法第一版明确不做。
- 跨会话搜对话原文。

## 五、测评重做

- 老项目的台账改成十来条长期功能，规矩写在各自的现状里，例如“导出”这条的现状写着“给财务用，列只能往后加”；“日期格式”放在项目的架构决定里，推翻的旧格式在历史表里。
- 提示仍只说“按我们之前定下的规矩来”，再加一条提示里换了说法的（用户说“添加时间”，台账写“创建日期”），检验目录兜底和别名。
- 再加一条与长期功能无关的小改动，检验它归到杂项而不是新建需求。
- 台账里预先放一对重复的需求，检验台账维护能把它们合并。
- 用 DeepSeek 跑，每个任务至少两次。
- 先用现有版本跑一遍新测评，作为改前的基线，再逐步对比。

### 改前基线（2026-11-22）

DeepSeek-V4.1-Flash，每个任务两次，台账照长期功能写了 13 条（重复需求题 14 条），日期规矩放在示例仓库的 `docs/adr/`。任务说明见 [测评说明](../scripts/eval/README.md)。

| 任务     | 结果                         | 查台账 | 新建需求 | 说明                                                                                            |
| -------- | ---------------------------- | ------ | -------- | ----------------------------------------------------------------------------------------------- |
| 老项目   | 0/2 通过                     | 5、2   | 2/2      | 第一次 list 写成 `(日期)`，没照“列表显示”现状里的 `[字段名 值]`；第二次合入卡在执行中，没合进去 |
| 换了说法 | 1/2 通过                     | 2、3   | 2/2      | 第二次把没有创建日期的老条目筛掉了，规矩只写在“创建日期”这条的现状里                            |
| 杂项改动 | 2/2 检查通过                 | 3、4   | 2/2      | 改版本号也新建了一条需求                                                                        |
| 重复需求 | 2/2 检查通过，0/2 合并重复项 | 0、2   | 1/2      | 现在没有台账维护，重复的两条都还在                                                              |

看出的问题：台账查了，但没有把相关几条的现状都读到再动手，漏掉的规矩恰好不在请求的字面里；与已有功能有关的请求、无关的小改动都被新建成了需求。

## 六、检索调研（2026-11-22）

问题：一个项目十几到几十条需求，用户的原话要找到对应的那条，换了说法也要找到。

| 做法                      | 结论                                                                                                                                                                      | 来源                                                                                                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 中文按两字一组 vs 分词    | 两字一组与分词效果相当，都明显好于按单字；分词准不准对检索影响不大。不需要分词库                                                                                          | [Microsoft Research](https://www.microsoft.com/en-us/research/?p=151541)、[NTCIR 2007](https://aclanthology.org/www.mt-archive.info/NTCIR-2007-Shi.pdf)                                                           |
| 字面打分 vs 向量          | 找重复的缺陷报告时，BM25 是很强的基线，有一份小测评里还略胜向量模型；向量只在说法差别大时有帮助，说法相近时反而更差                                                       | [文本差异与重复缺陷报告](https://arxiv.org/pdf/2212.09976)、[缺陷报告向量模型对比](https://arxiv.org/html/2308.09193v2)                                                                                           |
| 智能体记忆用 grep vs 向量 | 一篇 2026 年的论文在长对话记忆测评上，grep 在所有组合里都胜过向量；成绩主要取决于工具怎么给智能体用，不在检索算法。Claude Code 也放弃了本地向量索引，原因之一是索引会过时 | [Is Grep All You Need?](https://dev.to/pueding/is-grep-all-you-need-grep-vs-vector-retrieval-for-agentic-search-534k)、[编程智能体为什么不用 RAG](https://labuladong.online/en/interview/agent/coding-agent-rag/) |
| 让模型从候选里挑          | 模型从少量候选里判断很准，候选一多就变差；先用便宜的字面打分缩小范围，再让模型判断，是常见做法                                                                            | [LLM4Rerank](https://arxiv.org/pdf/2406.12433)、[检索加重排的商品匹配](https://www.zenml.io/llmops-database/semantic-product-matching-using-retrieval-rerank-architecture)                                        |
| SQLite 全文索引           | 自带的 trigram 分词至少要 3 个字，两个字的中文词查不好；要么自己做两字一组，要么带分词库                                                                                  | [FTS5 中文的两字一组做法](https://dev.to/foxck016077/sqlite-fts5-wont-tokenize-chinese-heres-the-7-line-bigram-fix-that-did-4fcc)、[FTS5 文档](https://sqlite.org/fts5.html)                                      |
| 记忆的定期整理            | mem0 的 Dream 在后台合并重复、把过时的标为被取代并保留历史；合并时新的必须包含旧的全部内容，拿不准就不动                                                                  | [mem0 Dream](https://mem0.ai/blog/dream-background-memory-consolidation-for-ai-agents)                                                                                                                            |

据此：

- 用两字一组的 BM25 字面打分，不上向量，不建全文索引：规模小，在内存里算即可，不会过时，也不依赖额外的模型。
- 说法不同的情况靠三样补：别名、需求少时总附全部目录、Main 自己读目录判断。
- 台账维护照 mem0 的规则：合并后保留全部内容，拿不准不合。与 mem0 不同，被并的一条挪完即删，不保留“已被取代”的记录：它的内容都已在合并后的需求里。
- 是否需要向量，看第五节测评里“换了说法”那题的结果再定。

## 七、步骤

1. 重做测评，用 DeepSeek 跑改前基线。
2. 需求改成长期功能：多条开发记录、现状、历史与别名、状态、杂项需求、看板一次工作一张卡，去掉决定，迁移数据。
3. 查找 `lookup` 和取上下文 `context`，开发开始时加别名。
