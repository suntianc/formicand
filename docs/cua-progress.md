# CUA 结果记录与恢复

本专项指南为中文。CUA 用 Pi 会话、trace、图片归档和下载文件保存进度，不另记进度笔记，也不引入独立的业务验证引擎。操作流程见 [CUA skill](../.pi/skills/cua/SKILL.md)，持久目录见 [数据布局](task-workspace-layout.md)。

Main 暂停后醒来、后端重启或进程被强杀后，都用 `--continue` 接着原来的 Pi 会话：已经送出的操作和它的结果仍在会话里；压缩时摘要取自完整历史。所以恢复时要回答的是“最后一次改变状态的操作有没有被核对过”，答案就在会话本身。

判断一次操作的结果时，看这几点：

| 要点     | 看什么                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------- |
| 预期结果 | 用户要得到的结果；例如“订单已保存且可从状态页查询”                                                  |
| 证据     | 实际文件路径、字节数/hash、`imageRef`、回执 ID 或可重查的状态页；只引用，不复制截图/base64/完整日志 |
| 核对方式 | 哪些由工具或文件复读确认，哪些仍是模型根据画面的判断                                                |

`dispatchStatus: sent` 只证明输入投递，`condition_met` 只证明指定 UI 条件。只有这些信号时，业务进度仍可为 `unknown`。文件存在不等于内容正确；需要时复读文件并核对内容/hash。视觉判断标明来源和局限，不伪装为机器检查。

Pi 会话与完整消息一直保存，图片和已接受的下载文件随 Task 保留。重启不恢复旧浏览器页面、VM `state` 或原生动作凭据。

恢复时先看会话里最后一次改变状态的操作：已有核对结果的，核对持久证据与当前状态即可；只有 `sent` 或 `unknown`、没有核对结果的，先只读查看实际状态（状态页、保存的文件、回执），再决定是否重做。不因超时、脚本重置或截图缺失而盲目重复提交；查不到结果也不能直接推断此前未执行，要如实说明。

完成仍由 Main 根据用户目标及证据判断；`finish_task` 的机械生命周期检查不代替业务验收。技能是模型执行约定，当前没有自动阻止一切重复业务操作的通用门禁。

回归见 [真实 Pi 进度恢复](../test/cua-progress-recovery-pi.test.js)：本地假模型驱动生产 Main/Pi、真实 Chromium、真实提交服务和文件核对，覆盖已核对与未核对两种进度在压缩后重启的恢复，以及输入已 sent、结果尚未核对时被 SIGKILL 的恢复；接续的会话保留已发操作，新进程先只读查证，再确认结果，并以服务端提交次数验证没有重放。它不证明任意真实模型都能正确判断业务完成。
